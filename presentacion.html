Arquitectura de una API REST con Express.js

Cómo organizar un servidor profesional separando Rutas, Controladores y Middlewares.

🍽️ La Analogía del Restaurante

• Express: El local y su infraestructura.
• Rutas: El recepcionista con la carta en la puerta.
• Controladores: Los chefs que cocinan el pedido.
• Modelos (Mongoose): La despensa de datos (Atlas).
• Middlewares: El equipo de seguridad y control de calidad.

🎯 Objetivo de la Arquitectura

Evitar el "código espagueti" en un solo archivo. Cada carpeta tiene una única responsabilidad para que el código sea limpio, escalable y fácil de mantener.

Concepto Base • Lámina 2 / 7

1. ¿Qué es Express.js?

Es el framework minimalista para Node.js que gestiona la comunicación HTTP entre el cliente (Frontend / Postman / Thunder Client) y nuestro servidor.

📥 Request (req) — Lo que entra

Contiene los datos que envía el usuario: parámetros en la URL (req.params), cuerpo JSON (req.body) o cabeceras.

📤 Response (res) — Lo que sale

Devuelve al cliente un código de estado HTTP (200, 201, 404, 500) y una respuesta clara en formato JSON.

const express = require('express');
const app = express();

// Middleware global: transforma el body
// entrante en un objeto JSON utilizable
app.use(express.json());

app.get('/', (req, res) => {
  res.status(200).json({
    success: true,
    message: 'API operativa'
  });
});
Organización • Lámina 3 / 7

2. Separación de Responsabilidades

En lugar de escribir todo en index.js, dividimos el backend en carpetas independientes:

📁 src/routes/

Solo dirige el tráfico. Conecta cada endpoint y verbo HTTP con su controlador. Prohibido hacer consultas a MongoDB aquí.

📁 src/controllers/

Contiene la lógica. Recibe la petición, llama al modelo de Mongoose y devuelve el JSON o envía el error a next(error).

📁 src/models/

Define los datos. Esquemas de Mongoose con tipos de datos y reglas de validación (required, min, enum).

📁 src/middlewares/

Protege el servidor. Captura rutas que no existen (404) y centraliza todos los errores (500) sin que la app se caiga.

Capa 1 • Lámina 4 / 7

3. Las Rutas (Routes): El Mapa de Endpoints

Las rutas leen el Verbo HTTP + la URL y ejecutan la función correspondiente del controlador.

// src/routes/productRoutes.js
const express = require('express');
const router = express.Router();
const {
  getAllProducts,
  getProductById,
  createProduct,
  updateProduct,
  deleteProduct
} = require('../controllers/productController');

router.get('/', getAllProducts);
router.get('/:id', getProductById);
router.post('/', createProduct);
router.put('/:id', updateProduct);
router.delete('/:id', deleteProduct);

module.exports = router;

✅ Buenas Prácticas REST

• GET /api/products → Listar todos
• GET /api/products/:id → Obtener uno
• POST /api/products → Crear nuevo
• PUT /api/products/:id → Actualizar
• DELETE /api/products/:id → Eliminar

💡 Regla de Oro

Un archivo de rutas limpio se lee como un índice: cero lógica de base de datos, cero bloques try/catch.

Capa 2 • Lámina 5 / 7

4. Los Controladores (Controllers): El Cerebro

Son funciones asíncronas (async/await) que procesan la petición, consultan MongoDB Atlas y devuelven una respuesta JSON coherente.

// src/controllers/productController.js
const Product = require('../models/Product');

const createProduct = async (req, res, next) => {
  try {
    // 1. Crea documento en Atlas con req.body
    const saved = await Product.create(req.body);

    // 2. Responde con código 201 y JSON
    res.status(201).json({
      success: true,
      data: saved
    });
  } catch (error) {
    // 3. Delega cualquier fallo al Middleware 500
    next(error);
  }
};

🔍 ¿Qué hace el Controlador?

1. Extrae datos de req.params o req.body.
2. Ejecuta métodos de Mongoose (find, findById, create...).
3. Verifica si el recurso existe (si no, devuelve 404).

⚡ ¿Por qué usamos next(error)?

En lugar de repetir respuestas de error en cada función, next(error) envía el fallo directamente al manejador centralizado 500.

Capa 3 • Lámina 6 / 7

5. Los Middlewares: Guardianes de la API

Funciones intermedias que interceptan la petición. En nuestra API destacan los dos middlewares de cierre para gestionar errores:

// src/middlewares/errorMiddleware.js

// 1. Middleware 404 (3 parámetros)
const notFound = (req, res, next) => {
  res.status(404).json({
    success: false,
    message: `No existe: ${req.originalUrl}`
  });
};

// 2. Middleware 500 (4 parámetros OBLIGATORIOS)
const errorHandler = (err, req, res, next) => {
  res.status(500).json({
    success: false,
    error: 'Error del servidor',
    message: err.message
  });
};

⚠️ El Orden Importa en index.js

1º app.use(express.json())
2º app.use('/api/products', productRoutes)
3º app.use(notFound) (404)
4º app.use(errorHandler) (500)

🔑 Detalle de Examen

Express reconoce un middleware de error exclusivamente porque tiene 4 argumentos: (err, req, res, next).

🚀 Resultado para la Entrega

Una API modular donde las rutas dirigen, los controladores ejecutan, Mongoose valida contra Atlas y los middlewares garantizan que el servidor siempre responda con un JSON limpio.
